## 2. What was built

- **Ids** (`internal/tenant/actions.go`). New requests are written as `ledger:tenant/<tenant>/<seq>`. Lines are read in either form. A result's legacy `request` is served and joined in this tenant's form (`NormalizeID`).
- **Migration at boot** (`internal/tenant/migrate.go`, before the ledger is read, under the file lock). Each action line's `id`, and a result's `request`, take the tenant form, keeping the number. `legacyId` goes right after `id`. Each following `prev` is rewritten to the new hash. Other members and the member order are untouched. The file is copied to `ledger.jsonl.<stamp>.bak` beside it, and a ledger with nothing to migrate is untouched.
- **The tenant-actions layer** (`internal/server/actions_layer.go`, through the new `store.Derived` in `internal/store/derived.go`).
  - Nodes: the ledger's lines (LedgerEntry), then the principals the requests name.
  - Edges: `prev` (newer to older), `request` (result to request), `subject` (request to container) and `principal` (request to principal).
  - Source block: Emitter.Ledger at the mounted agent ledger layer's version; with no such layer, the newest pushed Emitter.Ledger card's version; with neither, no source block.
  - Rebuilt on the first read of the layers after the file grows, so Portal's appends and the Runner's both show up with no restart. Mounted while the ledger holds an action line. The name is reserved (400).
- **Actions page** (`web/actions.js`, `web/portal.js`): a new `id` column. A row click opens `/<tenant>/graph/explore?from=<id>&direction=out&depth=5`, and the action cell still links the entry page.
- **Contract** `docs/api/actions.md`: the line shapes, the ids section (exact format and regex, the root, the migration rule, what the Runner must write), and where the ids show.
- **Spec and ontology**:
  - `api/openapi.yaml`: descriptions in the tenant form, optional `legacyId` on ActionRequest, and the reserved layer name. `internal/gen` is regenerated, and no operation was added.
  - `ontology.yaml` 0.16.1: edge Kinds `request`, `subject` and `principal`, and property `legacyId` on LedgerEntry.

## 5. Decisions (each in docs/design.md 55)

- **Asked: the query direction.** With the edges as specified, `direction=in` from a result reaches only newer lines. You chose to keep the edges and use `out` for the Actions row link and this report's query.
- **`prev` stays the SHA-256 hash, not an id.** The prompt had "kind, request, prev all use the new form". `kind` is no id. `prev` is what `GET .../ledger` and the Runner verify the chain with (design.md 45), so making it an id would break every chain check. The migration recomputes it so the chain stays valid, and the layer's `prev` edge carries the id link.
- **A broken link stays broken.** A `prev` is rewritten only where it named the old hash of the line before it.
- **The migration runs at every boot and only touches legacy lines.** Until Portal.Agent writes the new form, a legacy result it appends is read as this tenant's, and the next boot migrates it, with a new copy. A ledger with a line that is no ledger entry is not migrated; the boot then stops on that line as before.
- **Backups are never overwritten** (`.<n>.bak` when the name is taken) and are gitignored (`tenants/*/ledger.jsonl.*.bak`, added to `.gitignore`).
- **The layer is mounted while the ledger holds an action line.** A ledger of pushes alone gets none. Its nodes are every line, so `prev` is the real chain.
- **The layer survives restarts by being rebuilt**, not by being written. "Approved" in the prompt means approved snaps keep their own mounts. tenant-actions is never on disk and is rebuilt from the ledger at boot.
- **The agent chain excludes `ledger:tenant/...`** explicitly (`store.isAgentEntry`), since `ValidID` now accepts it.
- **The three new edge kinds are declared in `ontology.yaml`**, because the layer's module is Portal.
- **`GET .../layers/tenant-actions/nodes`** serves a new envelope as for any layer: no source block, and no `subject` edges ending in another layer. The tenant graph and the query have them.
- **CLAUDE.md's write rule** now names the migration's in-place rewrite and its copy as the one exception to append-only.
