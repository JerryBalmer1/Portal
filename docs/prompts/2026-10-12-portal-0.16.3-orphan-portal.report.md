The assessment was written in this conversation after the 2026-10-12 Refresh stopped at step 3. The user asked for the change to be made here, edit and stage only, with this report.

Result: done.

- Manual check list items 0.4, 3.3, 3.4 and 3.9 (new) were run and their Expects match.

## What happened, and what is still unknown

- Refresh 2026-10-12T08-12-34Z step 2, Portal `Down`, printed `No portal is recorded in C:\__Code\Portal\artifacts` and passed.
- Step 3, `Dev`, then failed: `port 8200 is in use by portal.exe~ (process 109484)`.
- That process was `build\win-x64\portal.exe -port 8200 -artifacts C:\__Code\Portal\artifacts ...`, started 2026-10-11 22:00:57. Its `portal.json` was gone.
- `portal.exe~` is Go's doing. On Windows, `go build` renames an in-use target to `<name>~`, and the running process then reports that name.
- The process was stopped by hand before this task.
- **What removed the record is not known.** Pester and Smoke use only TestDrive and `artifacts/smoke`. The one test that runs the real `Invoke-Build Dev` refuses at DevGate.
- One candidate is in the code. `Stop-Portal` silenced `Stop-Process` and `Wait-Process`, then removed `portal.json` regardless. A failed stop therefore left a running portal that no later Down or Up could see.
- The fix closes every path to that state rather than guessing which one was taken.

## What changed (docs/design.md 57)

- **`Get-PortalProcess`** (new, private) decides what counts as this repo's portal. It returns the live processes whose image is `<repo>\build\win-x64\portal.exe` or `portal.exe~`, as full paths. With `-Artifacts`, it keeps only those whose `-artifacts` is that directory: full path, no trailing separator, case-insensitive. It returns ProcessId, Port, Artifacts and Path. `-Process` takes fake rows for Pester.
- **`ConvertFrom-PortalCommandLine`** (new, private) splits a command line by the Windows `CommandLineToArgvW` rules, so a value reads as the portal read it. It takes `-name value`, `--name value` and `-name=value`.
- **`ConvertTo-PortalDirKey`** (new, private) turns a directory into one comparable string.
- **`Stop-Portal`** stops the recorded portal and every unrecorded one over the same artifacts, saying which with `-Verbose`.
  - A recorded id that fails the `Get-PortalProcess` test is never stopped, and its record is dropped. Before, Stop-Portal force-stopped whatever held that id, including an unrelated program after id reuse.
  - The record is removed only when nothing survives. A portal still running 10 s after `Stop-Process` keeps `portal.json`, and Stop-Portal throws naming it.
- **`Get-PortalStatus`** has a new property, `Recorded`. An unrecorded portal reads `Running` true and `Recorded` false, with its port from its command line. A record whose process is not such a portal reads as not running.
- **`Invoke-PortalUp`**: help text only. It already asks Status and calls Stop-Portal, so `Up`, `Dev` and `Feeds` now replace an unrecorded portal. So do Refresh steps 2 and 3, and Portal.Emitters' `Restart-Portal`, which calls Down then Dev.
- **`Start-Portal`** refuses a second portal over the same artifacts, recorded or not. The message is entry 32's plus `, unrecorded` and the directory. When this repo's portal over other artifacts holds the port, the busy-port message adds `It is this repo's portal serving <dir>: Stop-Portal -Artifacts '<dir>' stops it.`
- **`Invoke-PortalRefresh`**: after Portal's own down step, `Assert-PortalPortFree` checks the port Up uses. If it is held, the step fails as `FAILED after Down: <owner> (<step line>)`. This is a new handler, `portfree`, which Pester replaces.
- **`.build.ps1`**:
  - `Build` first removes any `build/win-x64/*.exe~` that no process runs.
  - `Status` prints `running (process <id>, unrecorded)` for an unrecorded portal.
  - `Down` gets a comment.
- **Version 0.16.3** in `Portal.psd1`, `ontology.yaml`, `ontology.go`, `api/openapi.yaml` (`internal/gen` regenerated), the tests, README and ONTOLOGY.md. No API, Kind or binary change.

## Choices made without asking (docs/design.md 57)

- Entry 32 is narrowed, not replaced. Unrecorded **and** this repo's binary **and** the same `-artifacts` is stopped. Any other port owner is still never touched.
- The fix sits in the module (Stop-Portal, Get-PortalStatus, Start-Portal), not in each task, so every caller gets it.
- A recorded process id is trusted only when it passes the same test as an unrecorded one.
- Stop-Portal throws and keeps the record when a portal survives, rather than warning.
- Refresh's port check runs only after Portal's own down step (`Repo` Portal, `Phase` down).
- `Build` removes stale `*.exe~` silently and leaves one in use alone, without a warning. Up's Build always runs while the old portal still runs, so a warning would print on every replace.
- `Get-CimInstance` runs with `-Verbose:$false`, so `Invoke-Build Down` (which calls `Stop-Portal -Verbose`) prints only Portal's own lines.
- Not covered: a portal that a crashed Pester run left on 18200 over a TestDrive directory already deleted. Start-Portal's message names it, but nothing stops it on its own.

## Worth a second look

1. **Item 0.4 of the manual check list was corrupted in 0.16.2.** `...\docs\refresh` and `...\artifacts\refresh` had become a carriage return and a bell character in the committed file. The same happened in this task: a backslash in an inline shell heredoc was unescaped before Python saw it, so `\r` and `\a` became control characters. Edits here went through script files and the Edit tool, and every edited file was scanned for control characters. A later agent editing paths with backslashes should do the same.
2. **What deleted `artifacts/portal.json` on 2026-10-11 is still unknown.** The fix makes the state recoverable and loud. It does not identify who caused it.
3. **`tenants/default/portal.yaml` is modified to `mode: dev` and unstaged.** Pester passes only because it is unstaged. Leave it out of the commit.
4. **Portal.Agent's Down still warns about a stale PORTAL_TOKEN** (a 401 in step 1 of the failed Refresh). This is prompt A of the 0.16.2 report, still open in Portal.Agent.
5. Each `Stop-Portal` and `Get-PortalStatus` call now runs one `Win32_Process` query, about 0.1 to 0.3 s. Pester's runtime did not visibly change (4:27 against 4:47).
