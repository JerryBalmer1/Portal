# 0.16.0: the tenant graph query — report

The task: one API that answers multi-hop questions across every mounted layer of a tenant. It walks breadth-first and in memory, and returns a normal envelope. The tenant graph's `?source=` becomes one case of it. Graph/Explore gets a query bar, and every graph node gets Query from here on right-click. Decisions are in docs/design.md 54. The parameter reference and the worked examples are in docs/api/query.md.

## The API, as built

```
GET /api/tenants/{t}/query?from=<ids>|kind=<Kind>[&follow=<kinds>][&direction=out|in|both][&depth=0..10][&until=<Kind>][&where=k=v]...[&source=<emitter>][&limit=1..5000]
```

- Defaults: `direction=out`, `depth=3`, `limit=500`, `follow` every kind.
- The response is the envelope with `paths`, `query` (resolved) and `truncated`; `truncatedAt` appears only when truncated.
- 200 when empty. 400 `unknown_node` naming the id. 400 `bad_request` for no start, both starts, or a bad `direction`, `depth`, `limit` or `where`.

The walk:
- One hop at a time for every start together, each start with its own visited set.
- `where` gates both entry into the result and expansion, starts included. `until` stops expansion, but never at a start.
- Edges: every edge between two result nodes.
- The cap counts distinct result nodes. `truncatedAt` is the hop the walk was on.

### 1. A container's network neighbours

**The brief, as written, does not fit the data.** Emitter.Network's dev layer holds two `RemoteHost` nodes (`dns:localhost`, `127.0.0.1`, one `ResolvesTo` edge) and no container. ### 2. A Terraform module's resources

**Emitter.Terraform's layer has no module → resource edge.** Its only edges are `Calls` (module → module). A resource names its module in `properties.Module`, so the module's resources come from a `where`:

```
GET /api/tenants/default/query?kind=Resource&where=Module=module.network&depth=0   -> 200
nodes:  module.network/resource/null_resource.subnet (Resource, "subnet", properties.Module "module.network", Type null_resource, main.tf:9)
paths:  [module.network/resource/null_resource.subnet]
query:  {"from":[],"kind":"Resource","follow":[],"direction":"out","depth":0,"where":["Module=module.network"],"limit":500}

GET /api/tenants/default/query?from=module.network&follow=Calls&depth=10   -> 200: module.network, module.network.module.endpoint; edge module.network|module.network.module.endpoint|Calls
GET /api/tenants/default/query?from=root&follow=Calls&depth=10&source=Emitter.Terraform   -> 200: root, module.network, module.network.module.endpoint; path [root, module.network, module.network.module.endpoint]
```

### 3. The ledger chain from one entry, with direction=in

**Not possible as asked.** The `action.result` lines live in `tenants/default/ledger.jsonl`, which is no mounted layer, so the walk cannot reach them. Their ids, `ledger:<seq>`, are also the same strings as the agent chain's. The example walks Emitter.Ledger's agent chain instead (`agent-ledger`, `prev` edges from the newer entry to the older one). So `direction=in` walks forwards in time and `direction=out` backwards.

```
GET /api/tenants/default/query?from=ledger%3A25&follow=prev&direction=in&depth=3   -> 200
nodes:  ledger:25 policy.deny pre File.delete /work/policy-smoke.txt, ledger:26 agent.run exit 0, ledger:27 agent.stop, ledger:28 agent.egress-check directBlocked True
edges:  ledger:26|ledger:25|prev, ledger:27|ledger:26|prev, ledger:28|ledger:27|prev
paths:  [ledger:25, ledger:26, ledger:27, ledger:28]

GET /api/tenants/default/query?from=ledger%3A25&follow=prev&depth=3   -> 200
nodes:  ledger:25, ledger:24 policy.allow post File.write ..., ledger:23 policy.allow pre File.write ..., ledger:22 policy.allow post File.read /etc/hostname
paths:  [ledger:25, ledger:24, ledger:23, ledger:22]

GET /api/tenants/default/query?from=ledger%3A25&follow=prev&depth=10&limit=4   -> 200: the same four, truncated true, truncatedAt 4

GET /api/tenants/default/query?from=ledger%3A24&depth=0   -> 200: ledger:24 "policy.allow post File.write /work/policy-smoke.txt"
```

**The last call shows the id collision.** In the tenant ledger, line 24 is the Runner's `action.result` answering `ledger:23` (logs on `env:container/claude-agent-dev/ledger`). The query resolves the same id to the agent chain's entry 24.

## Choices made without asking (design.md 54)

- **`from` and `kind` together is 400**, not an intersection.
- **A start is always expanded**, even of Kind `until`. A start must pass `where`.
- **`where` keys.** `id`, `kind` and `name` are the node's fields; anything else is a dotted path into `properties` (`properties.` reads a shadowed one). The match is exact on strings, and on numbers and booleans as JSON; a list or a map never matches; several are ANDed. Example 1 shows the trap: `where=kind=container` asks for the node's Kind, so `properties.kind=container` is needed.
- **Paths end wherever the walk stopped.** That includes a dead end or an already-reached neighbour, not only `until` or depth; otherwise a walk shorter than its depth would list no path.
- **Truncation** counts distinct result nodes across starts. What was reached is served, with its edges and paths.
- **The response** is the envelope with extra top-level members, which Graph.Node's schema allows. The spec says it as `allOf`.
- **Explore keeps its address.** `query: true` on the Page turns the bar on, so the menu (a graph) says which page has it and no page id is hard-coded. Without a query in the URL, the Canvases are drawn under the bar as before.
- **The bar round-trips.** Direction's empty choice is "out (default)", so an absent or explicit `direction` survives a submit. `kind`, `where`, `source` and `limit` ride along hidden.
- **Path ids select and centre** their node; they do not navigate. At most 500 paths are listed.
- **Query from here** is the node menu's fifth item, so environment rows get it too. On Cytoscape graphs it is a menu of its own, since those had none.
- **The edge order of the tenant graph** now follows its `from` node's first appearance, not the layer order. Same set; no test or page depends on the order.
- **The tenant ledger is not in the walk.** The ledger example uses the agent chain and says why.
- **The worked examples ran on a separate port** over the dev tenant's layer files, so the running dev portal (mode dev, on 8200) was not restarted. Restarting it could drop mounts no approved snap records.
