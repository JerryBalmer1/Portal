# Portal 0.16.5: Refresh step 7 failed 401 because it never fetched a token

Prompt: `[WORKSPACE: Portal] — 0.16.5: Refresh step 7 fails 401 after step 6 succeeded; find why the catalogue step's token is dead and fix it`.

## Root cause

**Step 7 (`catalogue`) never fetched a token. It sent whatever `PORTAL_TOKEN` Refresh's own process had inherited from the shell, and Mount's restarts had made that token dead.**

- `Invoke-PortalRefresh`'s `catalogue` handler called `Invoke-PortalApi -Path '/emitters'`. `Invoke-PortalApi` sends `$env:PORTAL_TOKEN` when it is set.
- Refresh's process never sets `PORTAL_TOKEN` itself. Every invoke step, including each `Dev`, runs in a child `pwsh`, and the `PORTAL_TOKEN` that `DevMint` sets dies with that child. The only value Refresh's process can hold is the one it inherited from the shell that started it. An `Invoke-Build Dev` run earlier in that shell sets it "for this process", as Dev's own message says.
- Step 6 (`approve`) did fetch, from `GET .../dev-token`, so it sent the live token and passed. In its `finally` it then restored the inherited, dead value into `PORTAL_TOKEN`, 0 s before step 7 used it.
- The server refuses a bearer it does not hold even on a GET (`internal/server/tenant.go:31-39`, design.md 38). So a stale token gets 401 rather than being treated as anonymous. With no `PORTAL_TOKEN` set, step 7 would have passed as an anonymous read. That is why it failed only in a shell that had run `Dev` before.

- **Portal restarted three times in this run:** once in step 3, and twice inside Mount, each time on a new process (166104, then 125124, then 226824). Each start minted a new token.
- **`tenants/default/tokens.yaml` holds one dev-bootstrap hash, `5a2571bd…`, created `2026-10-13T18:46:58.968Z`.** That is SHA-256 of `9d98439f…`, the token from Mount's last `Dev`, and the portal serving it is the one Mount left running. That token is what step 6 fetched.
- **What step 7 sent is not in any log.** It sent no prefix, and no Refresh-level log existed. Its 401 means it sent a token that was neither `9d98439f…` nor `jerry`'s, and the shell's leftover `PORTAL_TOKEN` is the only source the code has.
- **Now each API step's line carries `dev token <first 8>...`,** and `artifacts/refresh/<stamp>/refresh.log` keeps every step's line.
- **Run 2026-10-12T17-57-07Z (10:57 local, the 2026-10-12 failure) has the same shape.** `04-emitters-mount.log` shows two mints.

### Jerry's hypothesis: a `Dev` missing after Mount, so Refresh holds step 3's token

**Not the cause.**
- Refresh never held step 3's token: it lived in the step 3 child process only.
- There is no gap after Mount either. Mount ends on its own `Dev`, so a portal with a live token is up when step 5 starts. Step 6 proves it: it fetched that token and passed.
- Adding a `Dev` after Mount would mint a fourth token and restart once more, and step 7 would still have sent the inherited stale one.

The other candidates, one by one:

| Candidate | Verdict |
|---|---|
| A token cached at module load | No. Nothing reads a token at import. `Invoke-PortalApi` reads `$env:PORTAL_TOKEN` per call, and that value was simply stale. |
| A different tenant or port | No. Both steps used `Get-PortalTenant` (`default`) and `Resolve-PortalUrl` (`artifacts/portal.json`, 8200). The 401 names tenant `default`. |
| Mount's own `Dev` minting a token Refresh never reads | True, but harmless by itself. No step should read a child's token. The fault was that step 7 read no token at all. |
| The catalogue step using a tokens.yaml path instead of dev-token | Close, but not quite. It used neither: it used the ambient `PORTAL_TOKEN`. tokens.yaml holds only hashes. |

## The fix

- **Every API-calling step fetches its token immediately before its call, never earlier.** `Invoke-PortalRefresh` has one path, `$callApi`: the URL, then `GET .../dev-token`, then the call with that token. `approve` and `catalogue` both use it. Refresh no longer reads or writes `PORTAL_TOKEN`.
- **New private `Get-PortalDevToken`.**
  - It sends no Authorization header. The route is anonymous, and a stale bearer would get 401 there too.
  - A 404 throws: `answered 404: the portal serves no dev token. It was started with Invoke-Build Up (or tenant <t> is not in mode dev), and Refresh needs the portal Invoke-Build Dev starts`.
  - Before this fix, `approve` swallowed a failed fetch and silently fell back to `PORTAL_TOKEN`.
- **`Invoke-PortalApi -Token`** sends the given token instead of `PORTAL_TOKEN`. Callers that pass no `-Token` behave as before.
- **The token's first 8 characters appear in each API step's line** (`dev token 9d98439f...`). A failed call adds `(sent dev token <8>..., fetched from GET /api/tenants/<t>/dev-token just before)`. The full token is never printed or logged; Pester checks that `refresh.log` lacks it.
- **`artifacts/refresh/<stamp>/refresh.log`** (new) holds the header and every step's line.
- **Progress:** an invoke step still running prints `15 s... 30 s... ` on its own line, before its result. The API steps are bounded by their own 10 s and 30 s timeouts and get no ticks.
- **No order change.** `order.psd1` and the sequence table are as they were. Conflict 4 in `docs/refresh/dependency-order.md` now reads **"Every Portal start mints a new dev token; fetch at use."**, explaining the 0.16.5 failure.

## Choices made without asking (docs/design.md 59)

1. No `Dev` added to the order: the evidence shows none is missing.
2. Fetch at use for every API step, through one code path, never `PORTAL_TOKEN`.
3. `Invoke-PortalApi -Token` rather than setting and restoring the environment variable.
4. Up-mode detection by dev-token's 404, the only signal the API gives. The message also covers "tenant not in mode dev".
5. A new `refresh.log` per run, so the API steps leave a record as the invoke steps already did.
6. Progress ticks on invoke steps only, inline on the step's line.
7. Version 0.16.5: `Portal.psd1`, `ontology.yaml`, `ontology.go`, `api/openapi.yaml` (version only; `internal/gen` regenerated), the tests' version pins, README, ONTOLOGY.md.

## Sibling repos

**No change is needed in Portal.Emitters.** Mount's `Dev` sets `PORTAL_TOKEN` in its own child, which is correct for its own calls, and Refresh no longer depends on any child's token. Portal.Agent's `Down` warning about a stale `.env` token is still open, as before (prompt B of the 0.16.2 report). This change neither causes nor fixes it.

## Notes

- **The shell Refresh ran from probably still holds a dead `PORTAL_TOKEN`.** Refresh no longer sends it. Other wrappers in that shell still do (`New-PortalSnap`, `Mount-PortalLayer`, `Publish-PortalCard`), and they will get the same 401 until it is cleared: `Remove-Item Env:PORTAL_TOKEN`, or open a new shell.
- **An inline bash heredoc unescaped `\\` here too,** as the 0.16.3 report warned. That broke one Python patch, which failed its assertion before writing anything. The rest went through script files and the Edit tool. Every edited file was scanned and has no control characters.
- **`tenants/default/portal.yaml` (mode dev) stays modified and unstaged.**
